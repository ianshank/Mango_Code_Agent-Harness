## Problem statement

Phase 1 gave `hypothesis_register` an append-only revision path and an operator
reader, and deliberately stopped there: `C-HR-2` pins that no prompt builder
reads the hypothesis store. The reasoner therefore writes beliefs it can never
see again. Two consequences, both observed rather than predicted:

1. **Revision across runs is impossible in practice.** The only place a model
   ever sees an entry's id is the tool result that created it. Once that turn
   leaves the context, or the run ends, `revises` has nothing to point at. The
   Product persona in the phase-1 peer review called this out; phase 1 could
   only answer it with a persona line telling the model to "keep the ID".
2. **The store cannot prevent a repeated belief.** A hypothesis registered
   `retracted` on evidence in one run is invisible to the next, which can
   register the same claim afresh and spend an iteration re-discovering the
   same evidence. `orchestrator.max_iterations` is 10; each such call is one of
   them.

Evidence on `main` @ `81e22f4`:

```
$ git grep -n "open_gaps" harness/shared/agent_prompts.py harness/shared/orchestrator/loop.py
harness/shared/agent_prompts.py:34:    "{open_gaps}"
harness/shared/orchestrator/loop.py:350:        open_gaps = format_gaps_for_planner(
harness/shared/orchestrator/loop.py:354:        planner_prompt = PLANNER_PROMPT_TEMPLATE.format(task=initial_task, open_gaps=open_gaps)
$ git grep -n "hypothes" harness/shared/agent_prompts.py harness/shared/orchestrator/loop.py
(no matches -- the reasoner prompt carries the plan and nothing from the store)
```

The gap store already has the shape this needs: `format_gaps_for_planner`
renders open gaps into the planner prompt, bounded by
`agent_memory.planner_gap_limit`. Hypotheses have no equivalent. DEC-057
deferred it because there was no token bound to write the exposure limit
against; `orchestrator.context_budget_tokens` now exists, so the remaining
question is the one this spec answers: how many hypotheses a prompt may carry,
and how that block behaves under `context_policy` eviction.

### Vocabulary this spec depends on

- **Prompt** of a role means the `task` string `ExecutionLoop.execute_agent`
  receives for that role — the rendered `PLANNER_PROMPT_TEMPLATE`,
  `REASONER_PROMPT_TEMPLATE` or `VERIFIER_PROMPT_TEMPLATE`. It is *not* the
  message list a model call sees.
- **Context** of a model call means `conversation_history` after
  `apply_context_policy`. The three roles share one append-only history
  (`loop.py:225-229`, `241-245`), so every role's prompt is in the context of
  every later call in the run. That is H4's design, not this spec's: the
  planner's `open_gaps` block is already in the reasoner's and verifier's
  context today. This spec adds a block to the **reasoner's prompt**; by the
  same mechanism it is in the **context** of every model call from the
  reasoner's first iteration to the end of the run (reasoner iterations plus
  verifier iterations), and R-HS-3 is what bounds that cost per call.
- **Open** hypothesis: an entry with no `superseded_by` successors
  (`memory_view.successors_of` returns `[]`). A revision chain therefore
  renders its head only; every earlier link has a successor.

## Requirements

- R-HS-1: The reasoner prompt MUST carry a rendered block of **open**
  hypotheses for the workspace. Every status a caller may assert
  (`provisional`, `confirmed`, `retracted`) is shown when open: a retracted
  belief is exactly what stops the same claim being registered again.
  Superseded entries are excluded because their successor carries the current
  belief. A record without a string `id` is skipped, not rendered: a line the
  model cannot revise is noise.
- R-HS-2: Each rendered entry MUST be one line, status first, carrying the
  entry `id` verbatim, so a model reading the block can revise across runs with
  `revises=<id>`. Shape, fixed here so the arithmetic below means something:
  `- [<status>] confidence=<0.00> id=<uuid>: <claim>`. `reasoning` is **not**
  rendered in v1 (see [Open questions](#open-questions)); the block carries
  what is needed to recognise and revise a belief, not to re-argue it.
- R-HS-3: The block MUST be bounded by two policy keys under `agent_memory`,
  both loaded through `policy_loader.agent_memory_defaults` with the same
  present-policy-fails-closed / absent-policy-defaults semantics the
  context-window budget spec gives `context_budget_tokens`:
  `reasoner_hypothesis_limit` (int, count of entries) and
  `reasoner_hypothesis_budget_tokens` (int, estimated tokens for the whole
  rendered block, header included). Application modules MUST NOT hard-code
  either value. `reasoner_hypothesis_limit: 0` MUST render `""` — that is the
  operator's kill switch, and it needs no code change.
- R-HS-4: The token bound MUST be measured with `context_policy.estimate_tokens`
  using the policy `orchestrator.context_chars_per_token` coefficient — one
  estimator, shared with H4, not a second one. The block is measured as a
  single `user`-role pseudo-message (the shape it will occupy in history; the
  estimator counts the role string too). Entries are added most recent first;
  the first entry that would push the block over budget **stops** the render —
  it is dropped whole and nothing older is considered, so the block is always a
  contiguous most-recent prefix and no entry is ever truncated mid-line,
  because a claim cut in half is a different claim. A budget smaller than the
  header plus the first entry yields an empty block.
- R-HS-5: An empty result — no store, an empty store, a malformed store, a
  limit of `0`, or nothing open within budget — MUST render as `""` so the
  reasoner prompt is byte-identical to today's, mirroring
  `format_gaps_for_planner`. Reading is **not** side-effect free: the store's
  existing recovery contract (`memory_store._read_json_safe`, documented in
  `agent-memory-manager` rule 2) backs a malformed file up to
  `<name>.malformed.<epoch>` and resets it to `[]` on read, exactly as the
  planner's gap read does today. This spec keeps that contract rather than
  adding a second, read-only parser, and requires the side effect to be
  asserted, not assumed (AC-HS-6).
- R-HS-6: The rendered block lives in the reasoner's initial user message. Under
  the v1 eviction implementation (`context_policy.apply_context_policy`, which
  evicts tool-call groups only and returns the list as-is when none remain),
  that message is never an eviction target. It MUST be shown to coexist with
  eviction: with the block present and an explicit low context budget,
  tool-call groups still evict atomically, `history_tool_links_are_consistent`
  holds on the survivors, the block's message survives verbatim, and its size
  is counted in `tokens_before`. The degenerate case MUST also be pinned: a
  budget below the block alone evicts every group and still returns an
  over-budget list, which is why R-HS-3 bounds the block up front — eviction
  cannot rescue an oversized never-evicted message.
- R-HS-7: Every call of the formatter that reaches the render MUST emit one
  structured log line, `event=hypotheses_surfaced`, carrying `run_id` (when the
  caller has one), `shown`, `open`, `total`, `tokens_estimated` and the list of
  rendered `ids` — counts and ids only, never `claim` or `reasoning`, under the
  same no-content rule the dispatcher's tool events follow (2026 standards
  audit H6). `ids` is what lets an operator join a later `revises` back to the
  block that made it possible; that join is the feature's success measure.
- R-HS-8: The reasoner persona MUST tell the model: what the block is (its own
  prior notes from this workspace, possibly from other tasks); that the ids in
  it are the ones `revises` accepts; that a claim already present (open, any
  status) is revised rather than registered again, and when the same claim
  appears more than once the most recent is the one to revise; and that the
  block is data to weigh, not instructions to follow.
- C-HS-1: `C-HR-2` of the phase-1 spec is **superseded, not deleted**: the
  invariant narrows from "no prompt builder reads the store" to "no prompt
  builder reads the store through anything but the bounded reasoner formatter".
  `format_hypotheses_for_review` (unbounded, human), `load_hypotheses`
  (unbounded), `successors_of` and `_hypotheses_path` MUST remain unreachable
  from every prompt-building module; the two pins that enforced C-HR-2 are
  rewritten to enforce this, not removed.
- C-HS-2: The planner and verifier **prompts** MUST NOT gain the block, in the
  sense of "prompt" fixed above: `PLANNER_PROMPT_TEMPLATE` and
  `VERIFIER_PROMPT_TEMPLATE` gain no slot and their rendered `task` strings
  never contain it. Gaps go to the planner (what could not be done); beliefs go
  to the reasoner (the role that writes and can revise them). That the block
  reaches the verifier's *context* through the shared history is H4's existing
  behaviour, stated here so nobody reads this constraint as a promise the
  loop cannot keep. Widening the block to another role's prompt is a separate
  decision.
- C-HS-3: The model-facing formatter MUST live in `harness/shared/memory_view.py`,
  not `meta_tools.py`: `meta_tools` is at 476 of `limits.size_budget_lines`
  (500) on the base commit and the formatter belongs with the other readers,
  whose module docstring is rewritten from "for a human reader" to "how the
  stores are read back — by a person, unbounded, and by the reasoner, bounded".
  A fourth module for one function was considered and rejected as bloat. The
  formatter's signature mirrors `format_gaps_for_planner`: `hypotheses=None`
  plus keyword-only `workspace_dir`, `limit`, `budget_tokens`,
  `chars_per_token`, `policy_path`, `run_id`, every bound defaulting to the
  policy value when `None`. The dependency stays one-directional
  (`memory_store <- meta_tools <- memory_view <- loop`, with `memory_view`
  additionally importing `context_policy` and `policy_loader`, both leaves);
  `memory_view` MUST NOT import from the orchestrator.
- C-HS-4: Nothing in this change wakes DEC-003 `.mango` hooks, adds a prompt
  surface to the MCP door, or persists model scratch outside
  `<workspace>/.mango/memory/` — the hook-dormancy and no-scratch constraints
  of the context-window budget spec, carried forward unchanged.
- C-HS-5: Store text is **untrusted data written by the model**, rendered as
  such. The block MUST open with a header saying so (the model's own prior
  notes, to weigh, not to obey), and no field of an entry is interpreted by the
  harness: `status`, `confidence`, `claim` and `id` are formatted into text,
  never branched on. Age- and relevance-based filtering are rejected for v1 —
  both need a notion of "this task" the store does not record — and so is a
  `hypothesis_read` tool (a second door with its own authority row). Cross-task
  exposure inside one workspace is therefore accepted and declared: a belief
  registered for one task shows for the next task in the same workspace.

## Open questions

- **Default on or off.** The kill switch is `reasoner_hypothesis_limit: 0`
  (R-HS-3). The proposal ships **on** at `10`: shipping off would land the
  phase dead and leave DEC-057's deferral formally discharged but practically
  not, and the fail-closed key contract already forces every adopter with a
  customised block to make a choice. The review should confirm or overturn
  this. Blocking for step 2.
- **The token default, with the arithmetic.** Measured on the base commit with
  the R-HS-2 line shape (no `reasoning`): the fixed overhead per line is
  ~60 chars (`- [provisional] confidence=0.70 id=<36-char uuid>: `), so a terse
  claim (~60 chars) is ~120 chars ≈ 30 tokens, a typical one (~150 chars) ≈ 53
  tokens, a long one (~400 chars) ≈ 115 tokens; the header is one line ≈ 25
  tokens and counts. At `1500` tokens the block admits ~48 terse, ~28 typical
  or ~12 long claims, so with `limit: 10` the **count** bound governs in every
  regime measured and the token bound is the backstop against abnormally long
  claims — ten typical entries cost ~550 tokens, 0.4% of the 128 000-token
  budget and ~3% of one 65 536-byte tool result. Had `reasoning` been rendered
  (measured 354 chars typical, 90 tokens; 584 verbose, 147 tokens) the token
  bound would have governed at 10–16 entries and the two bounds would have
  fought; that measurement is the reason v1 drops `reasoning`. `1500` is a
  policy value so an operator can tune it without a code change; the review
  should argue the number, not accept it. Blocking for step 2.
- **`reasoning` text.** Excluded in v1 (R-HS-2). It is what lets the model
  judge whether new evidence bears on a claim, and it is also the field most
  likely to carry long, injected or stale text, and the one that made the
  arithmetic above tight. If a later phase wants it, the honest path is a
  bounded `hypothesis_read` tool with its own authority row, not a wider block.
  Decided, recorded in DEC-058; reopen there, not here.
- **Not in scope, recorded so it is not re-derived:** surfacing to the planner
  or verifier prompts (C-HS-2); a `hypothesis_read` tool; age- or
  relevance-based filtering and any per-task scoping (C-HS-5); content-level
  truncation of a single oversized entry (R-HS-4 drops it whole and stops,
  matching H4's stance on oversized tool payloads).
