## Problem statement

Phase 1 gave `hypothesis_register` an append-only revision path and an operator
reader, and deliberately stopped there: `C-HR-2` pins that no prompt builder
reads the hypothesis store. The reasoner therefore writes beliefs it can never
see again. Two consequences, both observed rather than predicted:

1. **Revision across runs is impossible in practice.** The only place a model
   ever sees an entry's id is the tool result that created it. Once that turn
   leaves the context, or the run ends, `revises` has nothing to point at. The
   Product persona in the phase-1 peer review called this out; phase 1 could
   only answer it with a persona line telling the model to "keep the ID".
2. **The store cannot prevent a repeated belief.** A hypothesis registered
   `retracted` on evidence in one run is invisible to the next, which can
   register the same claim afresh and spend an iteration re-discovering the
   same evidence. `orchestrator.max_iterations` is 10; each such call is one of
   them.

Evidence on `main` @ `81e22f4`:

```
$ git grep -n "open_gaps" harness/shared/agent_prompts.py harness/shared/orchestrator/loop.py
harness/shared/agent_prompts.py:34:    "{open_gaps}"
harness/shared/orchestrator/loop.py:350:        open_gaps = format_gaps_for_planner(
harness/shared/orchestrator/loop.py:354:        planner_prompt = PLANNER_PROMPT_TEMPLATE.format(task=initial_task, open_gaps=open_gaps)
$ git grep -n "hypothes" harness/shared/agent_prompts.py harness/shared/orchestrator/loop.py
(no matches -- the reasoner prompt carries the plan and nothing from the store)
```

The gap store already has the shape this needs: `format_gaps_for_planner`
renders open gaps into the planner prompt, bounded by
`agent_memory.planner_gap_limit`. Hypotheses have no equivalent. DEC-057
deferred it because there was no token bound to write the exposure limit
against; `orchestrator.context_budget_tokens` now exists, so the remaining
question is the one this spec answers: how many hypotheses a prompt may carry,
and how that block behaves under `context_policy` eviction.

## Requirements

- R-HS-1: The reasoner prompt MUST carry a rendered block of **open**
  hypotheses for the workspace, where open means the entry has no
  `superseded_by` successors. Every status a caller may assert (`provisional`,
  `confirmed`, `retracted`) is shown when open: a retracted belief is exactly
  what stops the same claim being registered again. Superseded entries are
  excluded because their successor carries the current belief.
- R-HS-2: Each rendered entry MUST include the entry `id` verbatim, so a model
  reading the block can revise across runs with `revises=<id>`. This is the
  mechanism that makes phase-1 revision reachable in practice.
- R-HS-3: The block MUST be bounded by two policy keys under `agent_memory`,
  both loaded through `policy_loader.agent_memory_defaults` with the same
  present-policy-fails-closed / absent-policy-defaults semantics the
  context-window budget spec gives `context_budget_tokens`:
  `reasoner_hypothesis_limit` (int, count of entries)
  and `reasoner_hypothesis_budget_tokens` (int, estimated tokens for the whole
  rendered block). Application modules MUST NOT hard-code either value.
- R-HS-4: The token bound MUST be measured with `context_policy.estimate_tokens`
  using the policy `orchestrator.context_chars_per_token` coefficient — one
  estimator, shared with H4, not a second one. Entries are added most recent
  first and an entry that would push the block over budget is dropped
  **whole**; the block is never truncated mid-entry, because a claim cut in
  half is a different claim. A budget smaller than the first entry yields an
  empty block.
- R-HS-5: An empty result — no store, an empty store, a recovered malformed
  store, or nothing open within budget — MUST render as `""` so the reasoner
  prompt is byte-identical to today's, mirroring `format_gaps_for_planner`.
- R-HS-6: The rendered block lives in the reasoner's initial user message, which
  the context-window budget spec's eviction rule classes as a non-group message
  and therefore not an eviction target.
  It MUST be shown to coexist with `apply_context_policy`: with the block
  present and an explicit low context budget, tool-call groups still evict
  atomically, `history_tool_links_are_consistent` holds on the survivors, and
  the block's size is counted in `tokens_before`. The bound in R-HS-3 is what
  keeps a never-evicted message from consuming the budget H4 protects; this
  requirement is the proof that it does.
- R-HS-7: Every render MUST emit one structured log line, `event=hypotheses_surfaced`,
  carrying `run_id`, `shown`, `open`, `total` and `tokens_estimated` — counts
  and ids only, never `claim` or `reasoning`, under the same no-content rule the
  dispatcher's tool events follow (2026 standards audit H6).
- R-HS-8: The reasoner persona MUST tell the model what the block is, that the
  ids in it are the ones `revises` accepts, and that a claim already present
  (open, any status) is revised rather than registered again.
- C-HS-1: `C-HR-2` of the phase-1 spec is **superseded, not deleted**: the
  invariant narrows from "no prompt builder reads the store" to "no prompt
  builder reads the store through anything but the bounded reasoner formatter".
  `format_hypotheses_for_review` (unbounded, human) and `load_hypotheses`
  (unbounded) MUST remain unreachable from every prompt-building module; the
  pin that enforced C-HR-2 is rewritten to enforce this, not removed.
- C-HS-2: The planner and verifier prompts MUST NOT gain the block. Gaps go to
  the planner (what could not be done); beliefs go to the reasoner (the role
  that writes and can revise them). Widening is a separate decision.
- C-HS-3: The model-facing formatter MUST live in `harness/shared/memory_view.py`,
  not `meta_tools.py`: `meta_tools` is at 476 of `limits.size_budget_lines`
  (500) on the base commit and the formatter belongs with the other readers.
  The dependency stays one-directional (`memory_store <- meta_tools <-
  memory_view <- loop`); `memory_view` MUST NOT import from the orchestrator.
- C-HS-4: Nothing in this change wakes DEC-003 `.mango` hooks, adds a prompt
  surface to the MCP door, or persists model scratch outside
  `<workspace>/.mango/memory/` — the hook-dormancy and no-scratch constraints
  of the context-window budget spec, carried forward unchanged.

## Backward compatibility

Additive on every axis a caller can observe today:

- `REASONER_PROMPT_TEMPLATE` gains one slot that renders `""` for every
  workspace that has no open hypotheses, so existing runs and every existing
  test that asserts on the reasoner prompt see a byte-identical prompt (AC-HS-6).
- The two new policy keys follow the H4 contract exactly: absent policy file →
  built-in defaults mirroring the shipped block; present policy missing them →
  `PolicyError`. An adopter with a customised `agent_memory` block must add the
  two keys, which is the same migration H4 required for `orchestrator` and is
  called out in CHANGELOG.
- `format_hypotheses_for_review`, `load_hypotheses`, `make memory-show` and the
  store format are unchanged. Phase-1 entries need no migration: the filter
  reads `superseded_by` through `successors_of`, which already tolerates the
  scalar an earlier build of the phase-1 branch could have written.
- `C-HR-2` is superseded by `C-HS-1`, and the two tests that enforced it are
  rewritten rather than deleted, so the property they protected — no unbounded
  prompt text from the store — survives in a narrower, still-enforced form.

## Open questions

- **The two defaults.** `reasoner_hypothesis_limit: 10` mirrors
  `planner_gap_limit` and is easy to defend. `reasoner_hypothesis_budget_tokens:
  1500` is a proposal: about 1% of `context_budget_tokens`, enough for ~10
  one-line claims with reasoning at 4 chars/token, small enough that a
  never-evicted block cannot crowd the tool-call groups H4 exists to protect.
  It is deliberately a policy value so an operator can tune it without a code
  change; the review should argue the number, not accept it. Blocking for step 2.
- **Reasoning text in the block.** Including `reasoning` costs tokens but is
  what lets the model judge whether new evidence bears on the claim. The
  proposal includes it, bounded by the token budget. Alternative: claim, status
  and confidence only, with reasoning available on request — but there is no
  "on request" tool, so that would need one, which is out of scope. Blocking
  for step 3.
- **Not in scope, recorded so it is not re-derived:** surfacing to the planner
  or verifier (C-HS-2); a `hypothesis_read` tool (a second door into the store,
  with its own authority row); content-level truncation of a single oversized
  entry (R-HS-4 drops it whole, matching H4's stance on oversized tool payloads).
