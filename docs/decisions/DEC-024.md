# DEC-024: PR #60 merged with every CI run on its head red under a commit message claiming `make ci` and mypy c

## Context

Recorded as a governance decision on the historical pipe log.

## Decision

PR #60 merged into `main` with all three CI runs on its head (323-325) failed and a merge commit (`9d38670`) claiming "`make ci` ... passed" and "mypy ... clean"; the pushed code had reverted the DEC-023 `input_schema` rename, added a langgraph-dependent regression test no CI leg could satisfy, left a test patching a module path the decomposition had moved, and added ignore rules for a directory nothing creates. Nothing could have stopped the merge because `main` carried no ruleset (DEC-018's open item). Two controls adopted: (1) a ruleset export is committed at `.github/rulesets/main.json` requiring the nine status checks `test_ci_gate_coverage.py::TestRequiredStatusChecksListIsAccurate` derives from `python-package.yml` (strict, up-to-date-branch policy) plus one code-owner review, with `test_workflow_contracts.py` pinning the export's contexts to the derived names so the two cannot drift; applying it is a repository-settings action the owner performs by importing the file. (2) A stated rule in `CLAUDE.md`, `CONTRIBUTING.md` and the PR template: a verification claim in prose is not evidence, only the check runs on the pushed head are, and the `make ci`/`make lint-cold` tails are pasted rather than summarised. Considered and rejected: a CI job that fails when the PR body's Validation section is empty -- it is satisfiable by pasting anything and would train authors to paste, not to run; the ruleset is the control that would have blocked #60, the rule is the norm that explains why
