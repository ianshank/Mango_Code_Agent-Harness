# DEC-058: Open hypotheses are surfaced to the reasoner prompt, bounded by two `agent_memory` keys; `reasoning` is not rendered; C-HR-2 narrows to C-HS-1

## Context

DEC-057 gave `hypothesis_register` an append-only revision path and deferred surfacing the store into any prompt as "phase 2", on two grounds: there was no token bound to write an exposure limit against, and how many hypotheses a prompt may carry and how that block behaves under `context_policy` eviction were a decision of their own. The first ground fell when `orchestrator.context_budget_tokens` landed with audit H4 (PR #110). This record discharges the second.

Without a reader in the loop, revision was unreachable in practice: the only place a model ever saw an entry's id was the tool result that created it, so once that turn left the context or the run ended, `revises` had nothing to point at. And the store could not prevent a repeated belief -- a claim `retracted` on evidence in one run was invisible to the next, which could register it afresh and spend one of `orchestrator.max_iterations` re-discovering the same evidence.

The spec `docs/specs/hypothesis-surfacing.md` was peer-reviewed from four perspectives before implementation; two blockers and the findings that changed the design are recorded there and summarised below.

## Decision

**The reasoner prompt carries a block of open hypotheses.** `REASONER_PROMPT_TEMPLATE` gains a trailing `{open_hypotheses}` slot, filled by `memory_view.format_hypotheses_for_reasoner` at the call site in `ExecutionLoop.execute_loop`. *Open* means the entry has no `superseded_by` successors and a usable id: a revision chain renders its head only, and every settable status is shown -- a `retracted` line is exactly what stops the same claim being registered again. Each entry is one line, status first, carrying the id verbatim: `- [<status>] confidence=<0.00> id=<uuid>: <claim>`. The block renders `""` when nothing is open, so a workspace without hypotheses sends the pre-DEC-058 prompt byte for byte.

**Two policy keys bound it, and nothing else does.** `agent_memory.reasoner_hypothesis_limit` (shipped `10`, mirroring `planner_gap_limit`) caps the count; `agent_memory.reasoner_hypothesis_budget_tokens` (shipped `1500`) caps the estimated size of the whole block, header included, measured with `context_policy.estimate_tokens` and `orchestrator.context_chars_per_token` -- the estimator H4 already uses, not a second one. Both follow the H4 loader contract: a present policy missing either key fails closed with `PolicyError`; an absent policy file yields the built-in defaults. A limit of `0` renders nothing and is the operator's kill switch. The block is measured as the user message it becomes; entries are added most recent first and the first that would overflow **stops** the render -- dropped whole, nothing older considered -- so the block is always a contiguous most-recent prefix and no claim is ever cut in half.

The bound is load-bearing because eviction cannot help. The three roles share one `conversation_history`, and `apply_context_policy` evicts tool-call groups only, so the reasoner's user message is in the context of every model call from the reasoner's first iteration to the end of the run, the verifier's included -- exactly as the planner's `open_gaps` already is. The peer review's first blocker was a constraint that promised the verifier's *prompt* would not carry the block; the spec now defines "prompt" as the `task` a role receives and "context" as the budgeted history, states the constraint over prompts, and pins both the coexistence with eviction and the degenerate case where an oversized block survives every eviction and is sent over budget.

**`reasoning` is not rendered.** Measured on the base commit, a line with `reasoning` cost 90-147 tokens; without it, roughly 30-55. With `reasoning` the token bound would have governed at 10-16 entries and fought the count bound; without it the count bound governs in every regime measured and the token bound is the backstop against abnormally long claims -- ten typical entries cost about 550 tokens, 0.4% of the shipped `context_budget_tokens`. `reasoning` is also the field most likely to carry long, stale or injected text. If a later change wants it in front of the model, the honest path is a bounded read tool with its own authority row, not a wider block.

**Store text is data.** The block opens with a header saying whose notes these are (the model's own, from this workspace, possibly from another task), that they are evidence to weigh and not instructions to follow, and that a listed claim is revised with `revises=<id>` rather than registered again. No field of an entry is branched on anywhere in the harness. Age- and relevance-based filtering were considered and rejected for this version: both need a notion of "this task" the store does not record. Cross-task exposure within one workspace is therefore accepted and declared.

**The read is not side-effect free, and says so.** The peer review's second blocker: the spec called the formatter "reading only" while `memory_store._read_json_safe` backs a malformed store up to `<name>.malformed.<epoch>` and resets it to `[]` on read. That is the store's documented recovery contract, shared with the planner's gap read, and it is kept rather than shadowed by a second, read-only parser -- two readers of one file with different recovery contracts is the kind of split that drifts. A test asserts the tree change is exactly the documented recovery and nothing else.

**C-HR-2 narrows to C-HS-1.** Phase 1 pinned that no prompt builder read the store at all. That invariant is superseded, not deleted: a prompt builder may reach the store through `format_hypotheses_for_reasoner` and through nothing else. `load_hypotheses`, `format_hypotheses_for_review`, `successors_of` and the path helpers stay out of every prompt-building module. The two tests that enforced C-HR-2 are rewritten into that narrower pin -- a call-graph check shared as `hypothesis_reader_violations`, applied to every prompt-building module discovered under `harness/shared`, and proven non-vacuous by running the same function over fixture modules that violate it.

**Where the formatter lives.** In `memory_view`, with the operator reader, whose docstring now describes two readers bounded differently on purpose rather than "a human reader". A fourth module for one function was considered and rejected as bloat. `memory_view` gains imports of `context_policy` and `policy_loader`, both leaves, and imports nothing from the orchestrator; `meta_tools` stays under `limits.size_budget_lines`.

**Observability.** Every call emits one structured `event=hypotheses_surfaced` line carrying `run_id`, `shown`, `open`, `total`, `tokens_estimated` and the rendered `ids` -- counts and ids only, never `claim` or `reasoning`, under the no-content rule the dispatcher's tool events follow (audit H6). The ids are what let an operator join a later `revises` back to the block that made it possible; that join is the feature's success measure.

**Elsewhere.** The LangGraph implementer node renders the slot empty: that variant is parked (DEC-053) and surfacing the store there is part of a revival decision, not of this one. The one test that hand-rolled a three-key `agent_memory` block moved onto the shared `agent_memory_policy` helper, which copies the shipped block and so survives the two new keys. `policy-artifact.json` is rebuilt with `publish_policy_artifact.py build`, which is the tool that digests `governance-policy.json` (`make digest-regen` pins the per-stack mirrors, not this file).

## Consequences

A belief the reasoner writes is now a belief it can see again, revise across runs, and be stopped by: the phase-1 revision path is reachable in practice rather than only within the turn that created an entry. The cost is bounded up front by two reviewed policy values, visible per run in one log line, and removable by an operator with a policy edit. An adopter with a customised `agent_memory` block must add the two keys -- the same migration H4 required for `orchestrator`, and called out in CHANGELOG. The protected paths this change touches carry the per-file attestation on the landing PR, computed by `make attestation` rather than counted by hand (DEC-038). Audit M4 is fully remediated: the meta-tools are no longer write-only in any sense, and the residual DEC-057 recorded -- that no prompt read hypotheses -- is closed by this record.
