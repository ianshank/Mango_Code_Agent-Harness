# DEC-059: Agent memory directory denied to raw writes; dedicated syntax-validating code generation writing tool added

## Context

Two related capabilities were identified and delivered:
1. **Agent Memory Integrity (NS-37)**: Finding §2.1 of `docs/reports/2026-DEEP-PEER-REVIEW-MEMORY-INTEGRITY.md` and spec `docs/specs/agent-memory-integrity.md` demonstrated that `nemotron-reasoner` held raw write tools (`write_file`, `apply_patch`) alongside validated meta-tools (`hypothesis_register`, `knowledge_gap_log`). `write_policy.write_denial_reason` did not deny `.mango/memory/**`, allowing well-formed forged hypotheses to bypass status and confidence validation and surface into future reasoner prompts via `format_hypotheses_for_reasoner` (DEC-058).
2. **Dedicated Code Generation Writing Tool (NS-38)**: Writing code solely via raw string overwrite (`write_file`) lacked pre-write syntax validation, AST checks, and structured error reporting. A dedicated `generate_code` writing tool was requested to validate syntax (e.g. Python AST parsing, JSON decoding) before committing bytes to disk, while enforcing workspace confinement, policy decision points (`authorize_write`), and write denial rules.

## Decision

**Agent memory write-denial is enforced in `write_policy.py`.**
`write_denial_reason` now checks whether a candidate target lies within the agent memory directory (`.mango/memory/`) under both workspace-scoped resolution and legacy install-root resolution. Direct raw writes via `write_file`, `apply_patch`, and shell redirects (`run_command`) are denied before bytes reach disk. The denial message explicitly directs callers to the sanctioned meta-tools (`hypothesis_register`, `knowledge_gap_log`).

**`.mango/memory/**` is explicitly excluded from `protected_paths`.**
As established in C-AMI-1, adding `.mango/memory/**` to `governance-policy.json`'s `protected_paths` would cause ordinary meta-tool writes during agent execution to trip `enforcement_digest.py` as `enforcement_tampered`. The denial is strictly a tool-path and broker control.

**Cryptographic signatures over memory entries were rejected as redundant.**
The agent holds `read_file` and `test_execute` under `agent-policy.json`. Any signing key resolvable by the harness process is readable by the agent; authenticating "produced by code that held the key" provides no security barrier against an agent with full read authority. Structural path denial at the write door is the correct control.

**`generate_code` added to `NEMOTRON_TOOLS` with syntax validation.**
`generate_code` is advertised in `harness/shared/tool_schemas.py`, mapped to the `write` action in `agent_authority.TOOL_REQUIRED_ACTION`, and dispatched through `ToolDispatcher`. It validates Python syntax (`ast.parse`) and JSON syntax (`json.loads`) before writing, respects `overwrite=False`, checks workspace confinement and write policy, and emits structured log context. Planner and verifier roles are denied `generate_code` by authority checks.

## Consequences

- Direct poisoning of agent memory stores is closed across all writing tools and shell redirects without requiring HMAC keys or digest baseline bloat.
- The reasoner gains a robust, syntax-validating code generation writing tool that prevents broken files from landing on disk.
- Backwards compatibility is preserved: `write_file`, `apply_patch`, and existing meta-tool suites continue to function unmodified.
