# DEC-014: `make secrets`'s `gitleaks git` invocation (all three Makefiles) scanned every ref in the local clon

## Context

Recorded as a governance decision on the historical pipe log.

## Decision

`make secrets`'s `gitleaks git` invocation (root, harness/node, and harness/jvm Makefiles, identically) scanned every ref present in the local clone, not just the checked-out branch's own history. Discovered when PR #35's `secret-scan` job failed despite a clean local `make secrets`: a completely unrelated branch pushed concurrently on this shared repository (`feature/governed-run-console`, touching neither PR #35's diff nor its ancestry) carries a real leaked key, and CI's fresh `fetch-depth: 0` clone picked it up while a long-lived local development clone, missing that branch, did not. Confirmed with a from-scratch `git clone` plus `gitleaks git . --log-opts="HEAD"` vs. without it: 141 commits scanned (the checked-out ref's own ancestry, clean) vs. 144 (every local ref, the unrelated leak). `--log-opts="HEAD"` restricts the walk to the current ref, matching INV-1's actual intent -- a PR's gate must be actionable by that PR's author -- rather than the prior behavior, which failed any PR for a secret on a branch it neither touches nor controls. All three `secrets` targets now pass `--log-opts="HEAD"`

## Consequences

a secret on a branch that isn't part of the ref under test is no longer caught by that ref's own gate; it remains caught the moment that branch's own PR is opened and scanned under this same, now-correctly-scoped rule
