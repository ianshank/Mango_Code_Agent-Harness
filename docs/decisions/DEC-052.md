# DEC-052: The LangGraph graph fails closed on a recorded error and on absent evidence

## Context

Recorded as a governance decision on the historical pipe log.

## Decision

The LangGraph graph fails closed on a recorded error and on absent evidence, and `INV-LG-3` is retitled because its old name licensed the outcome it was never about. Five defects, each reproduced against the real `langgraph` package (1.2.11) rather than read off the source; spec `docs/specs/langgraph-fail-open-hardening.md`. (1) `@with_authority` recorded a denial into the `errors` channel and the graph carried on: neither router read `errors`, and `quality_gate_node` consulted it only when `test_results` was empty, which no path through the compiled graph produces because `evaluation_node` always appends a row -- so a denied planner returned `VERIFIED` over an empty plan, and `NEXT_STEPS.md`'s "INV-LG-4 is active" was true of application and false of enforcement. Containment and consequence are different properties: `INV-LG-3` asks only that an exception not crash the graph, which was always honoured, so it becomes *Contained* Error Channel Routing and the new `INV-LG-6` carries the verdict half. (2) The quality gate passed vacuously -- `evaluation_node`'s no-orchestrator row is `passed=0, failed=0`, and grading by `failed > 0` alone made zero executed tests indistinguishable from a green suite, which is DEC-024's shape inside the graph's own gate. (3) Terminality is decided once, in `langgraph/errors.py`: control-plane nodes block, `OBSERVATION_NODES` do not because INV-16 requires an observation-mode producer's failure to leave the incumbent path unaffected, and an unrecognised node blocks so an unclassified error fails closed. A blocking error routes straight to `escalate` rather than spending revision budget: `errors` is an `operator.add` accumulator no node clears, so a retry cannot remove the record that failed the gate and the alternative is burning `max_iterations` to reach the same terminal. (4) `runtime_config()` is the producer for the `configurable.policy` key R-LPW-4 and R-LPW-5 made their consumers read and that no caller ever wrote; `recursion_limit` was read once to be interpolated into a log line and `max_concurrency` not at all. (5) Worse, `config` never reached either router whatever the caller passed: LangGraph injects it only for an accepted annotation spelling (`KWARGS_CONFIG_KEYS`), and `config: Any` is skipped with a `UserWarning` no gate observed -- so R-LPW-4's wiring passed its unit tests, which call the routers directly where an ordinary Python default applies, and did nothing through a compiled graph. That is the DEC-024 shape one level up, an acceptance criterion satisfied on a path production never takes, and `INV-LG-7` plus `TestConfigInjectionContract` pin the spelling for all seven config-reading functions. `X | None` is not an accepted form under PEP 563. (6) The `plan_gate`/`clarify` cycle had no fixpoint -- `clarify_node` writes `plan_gate: "pass"` and `plan_gate_node` recomputes that key from an unchanged `plan_divergence` -- and terminated only at `GraphRecursionError`; `_route_plan_gate` gains an `escalate` exit at a policy-bounded attempt count. Three assertions that pinned the vacuous pass are rewritten to assert the graded outcome, one of them reading `verdict in ("VERIFIED", "FAILED", "BLOCKED", "")` -- the channel's whole domain, a criterion no implementation could fail. Nine mutation proofs, each reverting one half and confirming its tests go red. Review on PR #87 found the first fix incomplete and R-LGH-3 under-specified: the blocking-error check sat only at `quality_gate`, which is downstream of `implementer`, so a denied planner still ran the write-capable node and spent a revision -- `revision_count: 1 | patches: 1 ['stub.py']` -- reaching `BLOCKED` only after the write. The check now comes first in `_route_plan_gate`, ahead of the `pass` branch that reaches `implementer`, and the requirement says where it must live: at every route that can reach the write-capable node, not at the quality gate alone. A denial costs zero writes. That defect survived its own regression test, which asserted `revision_count == 1` under the message "the implementer ran more than once on a terminal error" -- an off-by-one framing of a case where one is already one too many, and the second time in this entry that a check could not fail for the reason it named. `CHANNEL_COUNT` stays 12 and `EXPECTED_NODE_COUNT` 10: the two new gate keys live in the existing `gate_status` dict. Accepted and stated rather than hidden: a run recording a control-plane error, and a run with no conclusive result, now end `BLOCKED` where they ended `VERIFIED`; no caller depends on either, since `autonomous_healing` re-runs its own suite to decide success and is the only caller of `build_graph`. Not closed here and named in the spec: `peer_reviewer` and `security_reviewer` are registered with no incoming edge, so `findings` is empty on every run -- wiring them in is an expansion of the graph and belongs with the in-or-out decision NS-31 and R-SR-27 own; six `GraphPolicy` fields remain read by nothing. `OBSERVATION_NODES` stays a code constant rather than a policy key, deliberately: it is graph topology, and a policy-driven security exemption list is one an adopter can widen to silently disable the fail-closed behaviour this entry adds -- `test_constant_triage.py` could not have forced this row either way, because its inventory discovers only int/float module constants and is blind to collections
