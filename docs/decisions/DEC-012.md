# DEC-012: `read_file` and `apply_patch` join the tool surface behind a new `read_policy.py`, the read-side cou

## Context

Recorded as a governance decision on the historical pipe log.

## Decision

read_file and apply_patch join the tool surface, alongside the read-side policy that had to exist first. read_policy.py is the counterpart to write_policy.py: without it, a read_file mapped to the `read` action would have bypassed command_actions.classify entirely -- `cat .env` already denies as secret_access, an action no role holds, but a direct filesystem read graded plain `read` would have returned NVIDIA_API_KEY into conversation_history, sent back to the model API on the next turn. command_actions.py now composes its credential-filename regex from read_policy.CREDENTIAL_FILENAME_ALTERNATION rather than restating it, so the shell-command door and the direct-read door share one definition instead of two that can drift; a parity regression test asserts this as a property over a corpus rather than a fixed list. apply_patch reuses write_denial_reason unchanged, inheriting write_file's protected-path and .git-segment denial rather than a second implementation; agent-policy.json is unchanged, and apply_patch grades as the same write action as write_file, so the verifier -- which holds no write -- receives read_file and not apply_patch (R-AC-8 preserved under the new tool's name)

## Consequences

read_file and apply_patch use explicit open(..., newline="") rather than Path.read_text/write_text, because the latter silently translates CRLF to LF on read and does not restore it on write, turning a one-word patch into a whole-file diff -- a defect caught only by testing a CRLF fixture byte-for-byte, not by any existing gate
