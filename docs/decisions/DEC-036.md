# DEC-036: `nemotron.top_p` becomes a policy key read by both stacks

## Context

Recorded as a governance decision on the historical pipe log.

## Decision

`nemotron.top_p` becomes a policy key, read by both stacks. The Node client hard-coded `top_p: 0.7` in two duplicated request-body literals; the Python bridge omitted `top_p` from its payload entirely. So the two stacks sent different sampling parameters to the same endpoint, and had done since the client was written -- a divergence `test_wire_format_parity_with_typescript` exists to prevent but cannot detect, because that test asserts the request succeeds rather than comparing the two bodies field by field (its docstring enumerated the fields from the Python payload alone, which is why `top_p` was missing from it). Adding the key to `harness/shared/governance-policy.json` required `policy_loader.NemotronDefaults`/`nemotron_defaults()` (exact-equality pinned by `test_policy_consistency.py::test_policy_loader_nemotron_fallbacks_mirror_policy`), the Node `NemotronPolicy` contract, and regenerating `harness/control-plane/policy-artifact.json`, which digests the shared policy (`publish_policy_artifact.py build`, not `make digest-regen` -- the per-stack mirrors carry no `nemotron` block and their root-of-trust digests are untouched). Value 0.7 preserves the Node behaviour exactly; the intended behaviour change is on the Python side, which now sends `top_p` where it previously let the provider default apply. The two duplicated literals collapse into `buildChatRequestBody` in `harness/node/src/ai/nemotron/request-body.ts`, a pure function taking the policy as an argument so a test can prove the body follows the policy it is given rather than one that happens to agree with the shipped file. `SAMPLING_BOUNDS` stays out of policy deliberately: the clamp ranges are the provider's accepted input domain, and a policy that widened them would describe a request the endpoint rejects
