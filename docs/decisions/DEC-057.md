# DEC-057: `hypothesis_register` gains append-only revision; the sequential-thinking MCP server is not adopted and surfacing hypotheses is deferred

## Context

The reference `sequentialthinking` MCP server was evaluated for this harness. It performs no reasoning: it validates a thought record (`thought`, `thoughtNumber`, `totalThoughts`, `nextThoughtNeeded`, optional `isRevision` / `revisesThought` / `branchFromThought`), keeps an in-process history, and returns bookkeeping metadata. Its value is the tool description acting as a prompt plus one tool-call boundary per step. Adopting it here would need an MCP client the harness does not have (`mcp_server.py` is outbound-only), a Node dependency and a stdio child process, a `TOOL_REQUIRED_ACTION` row, and an attested edit to `tool_schemas.py` -- and every thought would spend one of `orchestrator.max_iterations` (10) and append two messages to the single `conversation_history` the context-window budget program is trying to bound. The reasoner persona already demands a step-by-step "Sequential Proof" in its output, and the two meta-tools already cover the honest parts of the concept.

The one idea that maps onto a real gap is revision. Every hypothesis entry was written with `status: provisional` and nothing updated it, while the function docstring and the schema description both promised that hypotheses "can be updated or falsified later as evidence arrives" (2026 standards audit M4 recorded the meta-tools as write-only; NS-17 fixed it for gaps only).

## Decision

`hypothesis_register` accepts two optional, keyword-only fields: `revises` (the id of a prior entry) and `status` (`provisional` by default, `confirmed`, or `retracted`). A revision is append-only: the new entry carries the pointer, and the prior entry is kept verbatim and marked `status: superseded` with `superseded_by` set to the new id -- the same `supersedes` / `superseded_by` pair these decision records use. `superseded` is a transition the store makes, never a status the model can assert. A pointer to an entry the store no longer holds (FIFO-trimmed, or mistyped) is recorded anyway and the result says so; a status outside the three allowed values is refused with a `failed` tool outcome before anything is written, because `tool_arg_validation` deliberately does not model `enum`. The three required arguments, the `additionalProperties: false` closure, the `read` action and the retention bound are unchanged, and the MCP door picks the change up through the shared dispatcher registry without an edit (spec `docs/specs/hypothesis-revision.md`, R-HR-1..5, C-HR-1..2).

Two things are decided *against*. The sequential-thinking MCP server is not adopted, for the reasons above. And the store is not surfaced into any prompt by this change: that is phase 2, and it is new prompt text on every run that needs its own `agent_memory` limit; it is deferred until the context-window budget spec lands a token bound to write it against, rather than guessed now.

## Consequences

A revision without a reader is a better-shaped diary entry: it gives the verifier's evidence and the debug dump a record of what the reasoner believed and later retracted, and it costs one loop iteration per call. The shape chosen here (append-only, pointer on the new entry, transition on the old) means phase 2 can be added without migrating the store. Two protected paths (`harness/shared/orchestrator/dispatcher.py`, `.mango/agents/nemotron-reasoner.md`) carry the attestation on the landing PR.
