# DEC-057: `hypothesis_register` gains append-only revision; supersession is structural, not a status; the sequential-thinking MCP server is not adopted

## Context

The reference `sequentialthinking` MCP server was evaluated for this harness. It performs no reasoning: it validates a thought record (`thought`, `thoughtNumber`, `totalThoughts`, `nextThoughtNeeded`, optional `isRevision` / `revisesThought` / `branchFromThought`), keeps an in-process history, and returns bookkeeping metadata. Its value is the tool description acting as a prompt plus one tool-call boundary per step. Adopting it here would need an MCP client the harness does not have (`mcp_server.py` is outbound-only), a Node dependency and a stdio child process, a `TOOL_REQUIRED_ACTION` row, and an attested edit to `tool_schemas.py` -- and every thought would spend one of `orchestrator.max_iterations` (10) and append two messages to the single `conversation_history` the context-window budget program is trying to bound. The reasoner persona already demands a step-by-step "Sequential Proof" in its output, and the two meta-tools already cover the honest parts of the concept.

The one idea that maps onto a real gap is revision. Every hypothesis entry was written with `status: provisional` and nothing updated it, while the function docstring and the schema description both promised that hypotheses "can be updated or falsified later as evidence arrives" (2026 standards audit M4 recorded the meta-tools as write-only; NS-17 fixed it for gaps only).

## Decision

`hypothesis_register` accepts two optional, keyword-only fields: `revises` (the id of a prior entry) and `status` (`provisional` by default, `confirmed`, or `retracted`).

**Supersession is structural, not a status.** The first implementation mirrored a decision record's `supersedes` / `superseded_by` pair by setting the prior entry's `status` to `superseded`. Adversarial review found that this destroyed the one fact the store exists to keep: a hypothesis registered `confirmed` on evidence, then later revised, read back as `superseded` and the verdict its evidence produced was gone -- an in-place lossy edit on a store this decision describes as append-only. A decision record can afford that because its status *is* a lifecycle state; a hypothesis's status is an epistemic verdict, and the two do not belong on one field. So `status` keeps what the model asserted for the life of the entry, and the presence of `superseded_by` is what records that the entry was later revised. `superseded` is consequently not a status at all, and a call asserting it is refused like any other unknown value -- which is a stronger form of "not model-settable" than the original guard.

`superseded_by` is a **list** of successor ids, appended in order, for the same class of reason: revision fans out. A belief revised one way, then revised differently on further evidence, produces two entries both naming the original in `revises`, and a scalar recorded only the last -- leaving the store holding two contradictory views of one graph. A scalar written by an earlier build is migrated to a list rather than discarded, because the store outlives the code.

A `revises` pointer to an entry the store no longer holds (FIFO-trimmed, or mistyped) is recorded anyway and the result says so; where retention trims the prior entry in the same call, the result says that too rather than claiming a supersession the reader cannot find on disk. `confidence` is now held to the 0.0-1.0 range the schema advertises, on the identical justification that makes `status` hand-checked: `tool_arg_validation` models `type` but neither `enum` nor `minimum`/`maximum`, so a promise made in the schema is kept in the function or it is kept nowhere. Both refusals are `failed` outcomes emitted before the store is touched, and both log at WARNING -- the dispatcher grades a `failed` outcome at DEBUG (`FAILED` is not in `DENIALS`), so without that line a model looping on a bad argument is invisible at normal levels on both doors.

The three required arguments, the `additionalProperties: false` closure, the `read` action and the retention bound are unchanged, and the MCP door picks the change up through the shared dispatcher registry without an edit (spec `docs/specs/hypothesis-revision.md`, R-HR-1..7, C-HR-1..2).

**Module split, in three layers.** The revision path pushed `meta_tools.py` past `limits.size_budget_lines` twice -- once for the write path and again for the reader below -- so the module divides by what each part knows: `memory_store` is how a store behaves, `meta_tools` is what a record means and how the model writes one, and `memory_view` is how a person reads them back. The dependency runs one way, `memory_store <- meta_tools <- memory_view <- show_memory`. The generic store mechanics move to `harness/shared/memory_store.py`: the advisory file lock, malformed-file recovery, FIFO retention, and a single `append_locked` that both writers now share instead of carrying near-identical copies of the read-modify-write. `MEMORY_DIR` and the path helpers that read it deliberately stay in `meta_tools`, because they are this repository's layout rather than store mechanics -- and because relocating that constant would have silently broken every test that monkeypatches it, which is exactly what a first attempt at the split did. `harness.shared.memory_store` therefore now holds `DEFAULT_LOCK_TIMEOUT_S`, `DEFAULT_LOCK_POLL_S` and `MIN_LOCK_POLL_S`; DEC-039 accepted all three as true constants when they lived in `meta_tools`, and that acceptance is unchanged by the move -- they remain client-local resilience defaults for the advisory lock whose values matter only when no caller expressed a preference, so the constant-inventory rows follow the code rather than being re-argued.

**An operator can read the store.** DEC-057 justifies revision by the trail it leaves, and a record nothing can read is not evidence, so `make memory-show` (`harness/shared/show_memory.py`) prints both stores with each hypothesis's verdict and its place in the revision graph. This is not a reversal of the phase-2 deferral below: that deferral is about prompt tokens, and printing to a terminal on request adds none to any run. `C-HR-2` is pinned by a test asserting no prompt builder imports the reader.

Two things are decided *against*. The sequential-thinking MCP server is not adopted, for the reasons above. And the store is not surfaced into any prompt by this change: that is phase 2, new prompt text on every run needing its own `agent_memory` exposure limit. This was written while the context-window budget was still parked, and that part has since changed -- `orchestrator.context_budget_tokens` landed with audit H4 (PR #110) while this branch was open, so the token bound phase 2 needed to be written against now exists. The deferral stands on its remaining half: how many hypotheses a prompt may carry, and how that interacts with `context_policy`'s group eviction, are a decision and a spec of their own, not a number to guess inside this change. `C-HR-2` and its test keep the store out of every prompt until that work is done.

**Two review-bot findings, both real.** The "a vanished store reads as empty" recovery covered the store *file* but not its *directory*: `file_lock` opens `<store>.lock` beside the store, so a removed `.mango/memory/` raised `FileNotFoundError` before `_read_json_safe` could treat the store as absent. `append_locked` now recreates the directory best-effort before taking the lock -- there rather than in `file_lock`, because it is the append that promises store recovery and a bare advisory lock has no business creating directories for a path its caller chose. A permission error still propagates.

Separately, every acceptance criterion in the spec was left unticked, and `test_spec_selectors_collect.py` judges ticked criteria only, so none of the cited `pytest -k` selectors were mechanically checked. Ticking them found four that collected nothing: one class name that never existed, two tests renamed during review, and one whose selector needed quoting. That gate also had a blind spot of its own, fixed here: it approximated pytest collection with the `Test*` class prefix, but pytest collects a `unittest.TestCase` subclass whatever it is named, so every selector aiming at a `*Tests` case class was reported vacuous -- twenty-three tests in `test_agent_harness_wiring.py` alone were invisible to it. It failed closed on correct specs, which is the direction most likely to be worked around rather than fixed.

## Consequences

A revision without a reader is a better-shaped record: it gives the verifier's evidence and the debug dump a durable trail of what the reasoner believed, on what evidence, and what later overturned it, and it costs one loop iteration per call. The shape chosen here -- append-only, pointer on the new entry, successor list on the old, status never rewritten -- means phase 2 can be added without migrating the store, and means a reader can walk the graph in either direction and get the same answer. The protected paths this change touches carry the per-file attestation on the landing PR. That set is computed by `make attestation` from `validate_invariants`' own matcher rather than counted by hand: an earlier draft of this record said "three" while the branch touched more, which is the shape DEC-038 recorded when a hand-transcribed table overstated its own coverage. `make attestation-check` verifies the PR body against the real set in both directions.
