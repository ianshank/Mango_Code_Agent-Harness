# DEC-013: A local bare `ruff` resolving to 0.15.8 (vs

## Context

Recorded as a governance decision on the historical pipe log.

## Decision

Tech-debt/CI-enforcement batch (docs/specs/ci-enforcement-gaps.md, docs/specs/dependency-hygiene.md). Retracted mid-PR: an initial research pass claimed 3 live ruff findings (2 unused `noqa: E402` in harness/api_server/tests/test_main.py, 1 missing `noqa: BLE001` in harness/shared/write_policy.py) and "fixed" them; CI then failed `make ci-python`'s `lint-python` step on those exact two files with the OPPOSITE verdict (E402 live, the added BLE001 noqa unused). Root cause: this environment has a bare `ruff` on PATH resolving to 0.15.8, while `python -m ruff` -- what the Makefile, `make lint`, and CI's `pip install -r requirements-dev.txt` all actually resolve to -- is the pinned 0.6.9, and the two versions disagree on both rules for this exact code shape. Every local verification in this batch that used the bare `ruff`/`mypy` binary instead of `python -m ruff`/`python -m mypy` or a `make` target is unreliable; `main` was already clean under the pinned 0.6.9, so both files are reverted to their pre-PR state and no ruff fix ships in this batch. The same misdiagnosis initially caused harness/**init**.py and harness/api_server/**init**.py (added for namespace-package consistency: both packages are genuinely imported as harness.x.y, matching harness/shared/**init**.py's existing convention) to be added, then reverted after the bare-ruff run reported an unrelated lint-rule interaction; re-tested under the correctly-pinned `python -m ruff`, the two files produce zero findings, so they are restored and ship in this batch after all. `make lint-node` genuinely does crash (`typescript-eslint does not support TS 7.0`, a pre-existing `typescript` 7.0.2 / `typescript-eslint` 8.67.0 incompatibility in harness/node/package.json) -- an independent, Node-toolchain-side finding unaffected by the Python tool-version issue -- so wiring it into `ci` remains out of this batch, tracked as a follow-up in docs/specs/ci-enforcement-gaps.md's Open questions. A root `make audit` (pip-audit against a new requirements.txt, delegated to the Node stack's existing osv-scanner target) closes the `KNOWN_GAPS["audit"]` exception in test_ci_gate_coverage.py via a dedicated workflow job, mirroring how `secrets` is enforced outside `ci` rather than duplicated across matrix legs. requirements.txt splits the API server's runtime dependencies (fastapi, uvicorn, pydantic, httpx) out of requirements-dev.txt, which keeps installing both via a `-r requirements.txt` include, and joins protected_paths alongside it; pyproject.toml gains a mirrored `[project.dependencies]`. governance/broker.py's and check_dedup.py's JSON-parsing consolidates into harness/shared/governance_json.py, a non-raising classifier -- each caller still raises its own existing exception type and log message from the classification, so check_dedup.py's SystemExit(1)/"Malformed governance policy" pin and broker.py's broadly-caught ValueError are both unchanged. policy_loader.py, coverage_gate.py, and validate_invariants.py are deliberately excluded from that consolidation: docs/specs/policy-single-source.md already decided validate_invariants.py (and the runpy-invoked per-stack scanners) stay standalone-stdlib, and coverage_gate.py alone has upward of eight individually caplog-pinned SystemExit messages a shared raiser would have to reproduce exactly to be a safe, no-behavior-change merge. Considered and rejected: relocating harness/node/.governance/ to repository root -- DEC-005 already rejected exactly this (a root allowed-remotes.txt) because `.governance/**` is a declared-dormant protected_paths pattern; harness/CONTRACT.md gains a paragraph citing DEC-005 explicitly instead of a physical move. Also added: a root `install` target (harness/shared/install_hooks.sh) so a clone using only the root Makefile still gets the pre-push hook; header comments on harness/node/.github/workflows/ci.yml and harness/jvm/.github/workflows/ci.yml identifying them as reference templates GitHub never executes; the version string unified to pyproject.toml's 2.1.9 across README.md, docs/architecture/c4_architecture.md, and NEXT_STEPS.md, which had each drifted to a different value; harness/jvm/ explicitly labeled in README.md and harness/CONTRACT.md as an unadopted reference template with no live CI enforcement, rather than leaving a reader to infer that from INV-2/INV-3's prose alone -- no new CI wiring for that stack was in scope
