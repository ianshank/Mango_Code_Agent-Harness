# DEC-049: The verdict was forgeable by the agent it judges

## Context

Recorded as a governance decision on the historical pipe log.

## Decision

The verdict was forgeable by the agent it judges, and the fix is containment, not isolation (2026 standards audit B4, `docs/reports/2026-STANDARDS-AUDIT.md`). Reproduced end to end on `71223f1` through the real dispatcher, broker and process backend: as `nemotron-reasoner`, `write_file forge.py` then `run_command python3 forge.py` rewrote the protected `Makefile` so `test-python` was a no-op, and the next `VerificationRunner.run` returned `VERIFIED` on a workspace whose real suite fails -- `-f Makefile` pinned which file was read and nothing pinned what it said. Four things change. (1) `protected_paths` gains the code-execution surfaces the verifier's own `make test-python` run would honour: `GNUmakefile`, `makefile`, `setup.py`, `setup.cfg`, `pytest.ini`, `tox.ini`, `sitecustomize.py`, `usercustomize.py`, `*.pth` and `**/conftest.py`; nine are declared dormant in `test_protected_path_liveness.py` with the reason that no such file is tracked and the pattern arms the guard before an agent creates one -- the same shape as `.claude/settings.local.json`. `*.pth` rather than `**/*.pth` because fnmatch's `*` crosses `/`, so the one pattern matches root and nested alike while the `**/` form misses the root. (2) `command_actions` grades `make` by what it is told to read: `-f`/`--file`/`--makefile` with anything but the canonical `Makefile`, `-C`/`--directory`, `-E`/`--eval`, `-I`/`--include-dir`, a bundled short flag and any `NAME=value` variable override all grade `destructive`; `pnpm exec <x>` and `npx <x>` grade as `<x>` and are accepted only when `<x>` is a program `_BY_PROGRAM` already grades `test_execute` (tsc, vitest, eslint, pytest, make, ruff, mypy, coverage), with `<x>`'s own arguments graded as a bare invocation would be. The parsing lives in `governance/indirect_exec.py`, which owns the canonical makefile name `verification.py` now imports, because `command_actions.py` sits at 472 of 500 lines. (3) `VerificationRunner.snapshot_enforcement` records the sha256 of every `protected_paths` file in the workspace, called by `ExecutionLoop.execute_loop` before the first agent turn, and `run` refuses -- `BLOCKED`, termination `enforcement_tampered`, naming the files, typed into `HarnessCheck.tampered_files` so `derive_verdict` cannot grade past it -- if any changed, appeared or vanished. The set is the policy's own definition of the enforcement layer, read through the same matcher the CI gate and the write policy use; the digest is `write_policy.policy_digest`, the same sha256-over-bytes the control plane pins the bundle with (it keeps its own copy per DEC-019, and a test pins the three agree). A run with no baseline records one and warns rather than failing, so direct callers keep working; the walk prunes `validate_invariants.SKIP_DIR_PARTS` and costs about 0.1 s at the repository root. (4) `SECURITY.md` and a `_comment` block in `agent-policy.json` say what `broker.py` already said: containment, not isolation, with the remaining gap named. What this does NOT close, stated so it is not overclaimed: the script still runs. It can still read the on-disk `.env`, write `.git/hooks/*`, create a `GNUmakefile` that a later bare `make x` from any role would read, and open sockets. The digest check makes the *verdict* unforgeable by that route; it prevents none of the script's other effects. OS isolation of `ProcessBackend` remains the fix and its own spec. Two behaviour changes are accepted: an adopter that constructs `VerificationRunner(makefile=<other>)` is now denied by its own broker, and `make NAME=value target` is no longer an agent action
