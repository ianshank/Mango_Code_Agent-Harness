# DEC-037: `retry.ts`'s `JITTER_CEILING_MS` is a true constant, recorded separately because DEC-025 names neith

## Context

Recorded as a governance decision on the historical pipe log.

## Decision

`retry.ts`'s `JITTER_CEILING_MS` (200) is accepted as a true constant, with its own entry because DEC-025 does not cover it. DEC-025 accepts the Node resilience defaults on the stated ground that they have "no Python counterpart of the same shape", and names five constants -- `failureThreshold`, `resetTimeoutMs`, `halfOpenSuccessThreshold`, `baseBackoffMs`, `maxBackoffMs` -- none of which is this one, and it names neither `JITTER_CEILING_MS` nor `retry.ts`. A triage row citing DEC-025 for it therefore fails `check_row`'s linkage test, which is the correct outcome: `NEXT_STEPS.md` NS-16 called this "a triage row", implying a table edit, when the decision it would cite did not exist. The reasoning DEC-025 applies still holds and is restated here rather than assumed: the Python side jitters proportionally (`retry_policy.DEFAULT_JITTER_RATIO`, a dimensionless 0.25 of the computed delay), the Node side adds an absolute millisecond ceiling, so the two are not the same knob in two languages and have nothing to drift from. A governance threshold here would be `max_retries`, which is already policy-sourced on both sides. Recorded alongside three rows DEC-025 already justified but the inventory had never registered (`resetTimeoutMs`, `halfOpenSuccessThreshold`, `maxBackoffMs`) -- the table is the inventory, so a constant absent from it was unlinked in practice however well the decision read
