# DEC-017: `audit-matrix`'s first real run found 7 known CVEs across `starlette`/`click`/`python-dotenv`, all r

## Context

Recorded as a governance decision on the historical pipe log.

## Decision

The `audit-matrix` job's first real run after DEC-016's fix found 7 known vulnerabilities the moment its 3.9 leg could actually execute `pip-audit`: `starlette` 0.49.3 (PYSEC-2026-161/248/249/2280/2281), `click` 8.1.8 (PYSEC-2026-2132), and `python-dotenv` 1.2.1 (PYSEC-2026-2270), all resolved only under Python 3.9 -- the `audit` job's single-interpreter 3.11 scan and `audit-matrix`'s 3.10/3.12 legs all found nothing, confirming DEC-015's premise (`pip-audit`'s resolution is interpreter-specific) with a real example on its very first run. Checked every currently-published fix directly against PyPI metadata: `starlette` >=1.0.1 (every 1.x release up to 1.6.0), `click` 8.3.3 and every later 8.3.x/8.4.x/8.5.x release, and `python-dotenv` >=1.2.2 all declare `Requires-Python >=3.10`; `python-dotenv` 1.2.1 -- the vulnerable version actually resolved -- is the newest release still declaring `>=3.9`. No `requirements.txt` pin can therefore make this leg both install under 3.9 and be clean under 3.9 at the same time: the project's Python 3.9 floor (flagged, per the user's explicit choice on this PR's originating plan, as a backlog item only) is now carrying unpatchable known CVEs in the API server's own runtime dependency stack, not merely an EOL-interpreter housekeeping concern. The 3.9 leg of `audit-matrix` is marked `continue-on-error` (`dependency-hygiene.md` C-DH-3/AC-8) rather than left blocking indefinitely on a gap this PR cannot close without bumping that floor; the finding is not silenced -- it remains in the step's own output on every run, is recorded here, and is added as new evidence to the tracking issue for the deferred floor bump. 3.10 and 3.12 stay fully enforced, with no `continue-on-error` of any kind
