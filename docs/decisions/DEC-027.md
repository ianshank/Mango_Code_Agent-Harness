# DEC-027: `autonomous_healing.py` and `lats_optimizer.py` parked under `harness/shared/experimental/` (unchang

## Context

Recorded as a governance decision on the historical pipe log.

## Decision

`autonomous_healing.py` and `lats_optimizer.py` are parked under `harness/shared/experimental/` (tech-debt-hardening-plan R-TDH-18; plan open question 3 resolved as "park"). Both shipped in v2.3.0 as headline features and have never been reachable from a runtime path: no orchestrator, node, CLI or API imports them, `synthesis.lats_enabled` is `false` with no reader, and INV-15 keeps LATS off until an ablation gate exists. The modules are byte-identical after the move, still policy-sourced (`orchestrator.max_healing_retries`, `lats.*`), still fully tested (`test_autonomous_healing.py`, `test_lats_optimizer.py`, `make test-lats`, the LATS regression in `test_e2e_nemotron_triage_regression.py`) and still measured by the coverage gate; what changes is that importing them is now visibly opting into an experiment, and the README, harness/README and C4 document say so. The old import paths are shims that re-export the public names and emit a `DeprecationWarning` for one minor release (C-TDH-2). Wiring either capability into a runtime path is its own spec, gated on `synthesis.lats_enabled` for LATS. In the same change the `MangoMASOrchestrator` facade loses the three private pass-throughs that existed only for tests (`_tool_handlers`, `_run_hook`, `_dispatch_tool_calls`); their tests now address `dispatcher` and `hook_runner` directly. `execute_sequential_thinking_loop` is not one of them: `orchestrator-tool-registry.md` R-ORCH-4 pins it as public surface and `verdict-propagation.md` R-VP-11 requires its prose return, so it stays
